# Rust Data Entity Storage Methods

Catalog of significant data entity storage frameworks, libraries, and approaches for Rust repositories. Intended to support automated static analysis for extracting data entities (database tables, document collections, etc.).

---

## 1. Diesel ORM

- **Name**: Diesel
- **Type**: Relational ORM / Query Builder
- **Supported Databases**: PostgreSQL, MySQL, SQLite
- **Detection Signals**:
  - `Cargo.toml`: `diesel = { version = "...", features = [...] }` under `[dependencies]`
  - Include patterns: `use diesel::prelude::*;`, `use diesel::pg::PgConnection;`, `use diesel::mysql::MysqlConnection;`, `use diesel::sqlite::SqliteConnection;`
  - File patterns: `src/schema.rs` (generated by `diesel print-schema`), `diesel.toml` (config file), `migrations/` directory with `up.sql`/`down.sql` pairs
  - Config files: `diesel.toml` — contains `[print_schema]` section pointing to `schema_file`
  - Derive macros: `#[derive(Queryable)]`, `#[derive(Insertable)]`, `#[derive(AsChangeset)]`, `#[derive(Identifiable)]`, `#[derive(Associations)]`
- **Entity Definition Style**: Two complementary mechanisms:
  1. `schema.rs` — auto-generated DSL that defines tables via `table!` macro:
     ```rust
     // src/schema.rs (generated)
     diesel::table! {
         users (id) {
             id -> Int4,
             username -> Varchar,
             email -> Varchar,
             created_at -> Timestamp,
         }
     }
     diesel::table! {
         posts (id) {
             id -> Int4,
             user_id -> Int4,
             title -> Varchar,
             body -> Text,
         }
     }
     diesel::joinable!(posts -> users (user_id));
     diesel::allow_tables_to_appear_in_same_query!(posts, users);
     ```
  2. Struct derives — Rust structs map to tables:
     ```rust
     #[derive(Queryable, Identifiable, Debug)]
     #[diesel(table_name = users)]
     pub struct User {
         pub id: i32,
         pub username: String,
         pub email: String,
         pub created_at: chrono::NaiveDateTime,
     }

     #[derive(Insertable)]
     #[diesel(table_name = users)]
     pub struct NewUser<'a> {
         pub username: &'a str,
         pub email: &'a str,
     }
     ```
- **Extraction Approach**:
  1. Detect `diesel` in `Cargo.toml`.
  2. Locate `schema.rs` (check `diesel.toml` for `schema_file` path, default `src/schema.rs`).
  3. Parse `diesel::table! { table_name (pk_column) { ... } }` macro invocations in `schema.rs` — these are the authoritative table definitions. Extract table name (first token) and all column names with types.
  4. Also parse `joinable!` and `allow_tables_to_appear_in_same_query!` macros for relationship mapping.
  5. Glob for all `*.rs` files and search for `#[derive(Queryable)]`, `#[derive(Insertable)]`, `#[derive(AsChangeset)]`, `#[derive(Identifiable)]`.
  6. For each such struct, extract the `#[diesel(table_name = foo)]` attribute to get the table name override, or derive from struct name (snake_case, pluralized).
  7. Cross-reference struct fields with columns in `schema.rs`.
- **Key Challenges**:
  - `schema.rs` is generated by `diesel print-schema` and may not be committed to the repo (though it usually is). If absent, fall back to migration files.
  - Multiple schema files may exist for modular projects using Diesel's `allow_tables_to_appear_in_same_query!` across modules.
  - `#[diesel(table_name = ...)]` attribute is the authoritative table name; without it, naming convention (snake_case plural of struct name) is assumed.
  - Custom `sql_types` in Diesel can obscure column type mapping.
- **Analysis Tools**:
  - tree-sitter-rust: parse macro invocations (`macro_call` nodes) and attribute macros
  - Regex for `table!\s*\{([^}]+)\}` as fallback
  - `syn` crate (Rust proc-macro parser) for richer AST if a Rust-based analyzer is used
- **Complexity**: Low (schema.rs present) / Medium (schema.rs absent)

## 2. Diesel Migrations

- **Name**: Diesel Migrations
- **Type**: Migration Tool
- **Supported Databases**: PostgreSQL, MySQL, SQLite
- **Detection Signals**:
  - Directory structure: `migrations/<timestamp>_<name>/up.sql` and `migrations/<timestamp>_<name>/down.sql`
  - `Cargo.toml`: `diesel_migrations = "..."` in `[dependencies]`
  - Embedded migrations: `embed_migrations!()` or `diesel_migrations::embed_migrations!()` macro in Rust source
  - Config: `diesel.toml` with `[migrations_directory]` setting
- **Entity Definition Style**: Standard SQL DDL in `up.sql` files.
  ```sql
  -- migrations/2024-01-15-120000_create_users/up.sql
  CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(64) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
  );
  ```
- **Extraction Approach**:
  1. Detect `migrations/` directory (or configured path from `diesel.toml`).
  2. Sort migration directories by timestamp prefix.
  3. Process `up.sql` files in chronological order.
  4. Parse `CREATE TABLE`, `ALTER TABLE ADD COLUMN`, `DROP TABLE` to reconstruct final schema.
  5. Ignore `down.sql` files for schema extraction (they represent rollback operations).
  6. For `embed_migrations!()`, the migration directory is bundled at compile time — look for the macro to confirm migration management.
- **Key Challenges**:
  - Renaming or moving columns via `ALTER TABLE RENAME COLUMN` (PostgreSQL-only) needs special handling.
  - `DROP TABLE` in later migrations means the entity no longer exists in current schema.
  - Migrations directory path may be non-standard; check `diesel.toml`.
- **Analysis Tools**:
  - SQL parser (pg_query for PostgreSQL, sqlparser-rs for multi-dialect)
  - Glob + sort for migration file enumeration
- **Complexity**: Low

## 3. SQLx

- **Name**: SQLx
- **Type**: Raw SQL / Compile-time Checked Queries
- **Supported Databases**: PostgreSQL, MySQL, SQLite, MSSQL
- **Detection Signals**:
  - `Cargo.toml`: `sqlx = { version = "...", features = ["postgres", "sqlite", "mysql", ...] }`
  - Include patterns: `use sqlx::prelude::*;`, `use sqlx::{PgPool, MySqlPool, SqlitePool}`, `use sqlx::postgres::PgPoolOptions`
  - Macro usage: `sqlx::query!("SQL")`, `sqlx::query_as!("SQL", ...)`, `sqlx::query_scalar!(...)`
  - Derive macros: `#[derive(sqlx::FromRow)]`
  - File patterns: `migrations/` directory with `*.sql` files (same structure as Diesel migrations), `.sqlx/` directory (query cache for offline mode)
  - Config: `SQLX_OFFLINE=true` in `.env`; `sqlx-data.json` (legacy) or `.sqlx/*.json` files (query cache)
- **Entity Definition Style**: SQL strings in macros with optional struct mapping via `FromRow` derive.
  ```rust
  // Compile-time checked query (requires live DB or .sqlx cache):
  let users = sqlx::query_as!(User, "SELECT id, username, email FROM users WHERE active = $1", true)
      .fetch_all(&pool)
      .await?;

  // FromRow struct:
  #[derive(sqlx::FromRow, Debug)]
  pub struct User {
      pub id: i32,
      pub username: String,
      pub email: String,
  }

  // Runtime query (no compile-time check):
  sqlx::query("INSERT INTO events (event_type, payload) VALUES ($1, $2)")
      .bind(&event_type)
      .bind(&payload)
      .execute(&pool)
      .await?;
  ```
- **Extraction Approach**:
  1. Detect `sqlx` in `Cargo.toml`.
  2. Glob for `*.rs` files and extract SQL strings from:
     - `sqlx::query!("SQL", ...)` — first string argument
     - `sqlx::query_as!(Type, "SQL", ...)` — second string argument
     - `sqlx::query_scalar!("SQL", ...)` — first string argument
     - `sqlx::query("SQL")` — first string argument (runtime query)
  3. Parse extracted SQL strings for table names.
  4. Search for `#[derive(sqlx::FromRow)]` or `#[derive(FromRow)]` — these structs map to query result shapes.
  5. Parse `.sqlx/*.json` or `sqlx-data.json` offline query cache — these files contain the SQL text of all compile-time-checked queries.
  6. Process migration files in `migrations/` directory (same approach as Diesel migrations).
- **Key Challenges**:
  - `sqlx::query!` macros require a live database or `.sqlx/` cache for compile-time checking; the cached queries in `.sqlx/*.json` are an excellent static analysis source if present.
  - `query_as!` links a SQL query to a Rust struct, but the struct name is not necessarily the table name.
  - Raw `sqlx::query(...)` calls use runtime strings that may be dynamically constructed.
  - `sqlx::migrate!("./migrations")` macro confirms migration usage.
- **Analysis Tools**:
  - tree-sitter-rust: parse macro invocations, attribute macros, derive lists
  - JSON parsing for `.sqlx/*.json` cache files
  - SQL parser for extracted query strings
- **Complexity**: Medium

## 4. SQLx Migrations

- **Name**: SQLx Migrations
- **Type**: Migration Tool
- **Supported Databases**: PostgreSQL, MySQL, SQLite, MSSQL
- **Detection Signals**:
  - `Cargo.toml`: `sqlx-cli` as a dev dependency or build tool; `sqlx = { features = ["migrate"] }`
  - Directory: `migrations/` with files named `<VERSION>_<description>.sql` (e.g., `0001_create_users.sql`) or with `.up.sql`/`.down.sql` suffix
  - Macro: `sqlx::migrate!("./migrations")` in Rust source
  - Config: `DATABASE_URL` in `.env`
- **Entity Definition Style**: Standard SQL DDL in sequentially versioned files.
- **Extraction Approach**: Same as Diesel migrations — sort by version prefix, process `up.sql` or single-file migrations in order, reconstruct schema from `CREATE TABLE` / `ALTER TABLE` statements.
- **Key Challenges**: SQLx supports both reversible (`.up.sql`/`.down.sql`) and non-reversible (single `.sql` file) migrations; detection must handle both patterns.
- **Analysis Tools**: SQL parser, glob + sort
- **Complexity**: Low

## 5. SeaORM

- **Name**: SeaORM
- **Type**: Relational ORM (async)
- **Supported Databases**: PostgreSQL, MySQL, SQLite
- **Detection Signals**:
  - `Cargo.toml`: `sea-orm = { version = "...", features = [...] }`, `sea-query`, `sea-schema`
  - Include patterns: `use sea_orm::entity::prelude::*;`, `use sea_orm::*;`
  - Derive macros: `#[derive(DeriveEntityModel)]`, `#[derive(DerivePrimaryKey)]`, `#[derive(DeriveActiveModelBehavior)]`
  - File patterns: `src/entities/` directory containing one file per entity (SeaORM CLI convention)
  - Code generation: `sea-orm-cli generate entity -o src/entities` produces one `.rs` file per table
- **Entity Definition Style**: Each entity is defined in its own module with specific trait implementations and a `Column` enum.
  ```rust
  // src/entities/user.rs (generated by sea-orm-cli)
  use sea_orm::entity::prelude::*;

  #[derive(Clone, Debug, PartialEq, DeriveEntityModel)]
  #[sea_orm(table_name = "users")]
  pub struct Model {
      #[sea_orm(primary_key)]
      pub id: i32,
      pub username: String,
      pub email: String,
      pub created_at: DateTimeUtc,
  }

  #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
  pub enum Relation {
      #[sea_orm(has_many = "super::post::Entity")]
      Post,
  }
  ```
- **Extraction Approach**:
  1. Detect `sea-orm` in `Cargo.toml`.
  2. Check for `src/entities/` directory (SeaORM CLI convention) — glob `*.rs` files there.
  3. In all `*.rs` files, search for `#[derive(DeriveEntityModel)]`.
  4. For each such struct, extract the `#[sea_orm(table_name = "foo")]` attribute — this is the authoritative table name.
  5. Extract struct fields (`Model` struct) for column names.
  6. Parse `Column` enum variants for explicit column definitions.
  7. Parse `Relation` enum for foreign key relationships between entities.
  8. `#[sea_orm(primary_key)]` and `#[sea_orm(unique)]` attributes provide constraint information.
- **Key Challenges**:
  - SeaORM entities use `Model` as the struct name by convention; the table name is only in the attribute.
  - Custom entity implementations (not using `DeriveEntityModel`) require parsing `impl EntityTrait` manually.
  - `ActiveModel` structs wrap every field in `ActiveValue<T>`; don't confuse with `Model`.
- **Analysis Tools**:
  - tree-sitter-rust: attribute parsing, derive list parsing
  - Regex: `#\[sea_orm\(table_name\s*=\s*"([^"]+)"\)]`
- **Complexity**: Low

## 6. Sea-ORM Migrations

- **Name**: sea-orm-migration
- **Type**: Migration Tool
- **Supported Databases**: PostgreSQL, MySQL, SQLite
- **Detection Signals**:
  - `Cargo.toml`: `sea-orm-migration = "..."` in `[dependencies]` (often in a `migration/` workspace member)
  - File patterns: `migration/src/m<YYYYMMDD>_<HHMMSS>_<name>.rs` or `migration/src/m<VERSION>_<name>.rs`
  - Trait implementations: `impl MigrationTrait for MigrationStruct { ... }` with `async fn up(&self, manager: &SchemaManager<'_>)`
  - `migration/src/lib.rs` that lists all migrations in a `Migrator` struct
- **Entity Definition Style**: Rust code using `SchemaManager` / `sea_query` DSL rather than raw SQL.
  ```rust
  use sea_orm_migration::prelude::*;

  pub struct Migration;

  #[async_trait::async_trait]
  impl MigrationTrait for Migration {
      async fn up(&self, manager: &SchemaManager<'_>) -> Result<(), DbErr> {
          manager
              .create_table(
                  Table::create()
                      .table(Product::Table)
                      .col(ColumnDef::new(Product::Id).integer().not_null().auto_increment().primary_key())
                      .col(ColumnDef::new(Product::Name).string().not_null())
                      .col(ColumnDef::new(Product::Price).decimal().not_null())
                      .to_owned(),
              )
              .await
      }
  }

  #[derive(Iden)]
  enum Product {
      Table,
      Id,
      Name,
      Price,
  }
  ```
- **Extraction Approach**:
  1. Detect `sea-orm-migration` in `Cargo.toml`.
  2. Locate migration files (typically `migration/src/m*.rs`).
  3. In each migration file, find `Table::create().table(<Enum>::Table)` patterns.
  4. Find `#[derive(Iden)]` enums — the enum name (minus `::Table` variant) is the entity name; other variants are column names.
  5. `.col(ColumnDef::new(<Enum>::FieldName)...)` patterns enumerate columns.
  6. Cross-reference `Iden` enum names with entity names found in SeaORM entity files.
- **Key Challenges**:
  - SeaORM migrations use a Rust DSL (sea_query) rather than SQL; standard SQL parsers cannot be used.
  - `Iden` enum names may not exactly match table names (they often do via `to_string()` conversion to snake_case).
  - Raw SQL can also be executed within `up()` via `manager.get_connection().execute_unprepared("SQL")`.
- **Analysis Tools**:
  - tree-sitter-rust: parse enum definitions, method call chains, `#[derive(Iden)]`
  - Regex: `#\[derive[^\]]*Iden[^\]]*\]\s*enum\s+(\w+)`
- **Complexity**: Medium

## 7. Rusqlite

- **Name**: Rusqlite
- **Type**: Raw SQL / Thin SQLite Wrapper
- **Supported Databases**: SQLite
- **Detection Signals**:
  - `Cargo.toml`: `rusqlite = { version = "...", features = [...] }`
  - Include patterns: `use rusqlite::{Connection, Result}`, `use rusqlite::*`
  - Function usage: `Connection::open(...)`, `conn.execute("SQL", ...)`, `conn.query_row("SQL", ...)`, `conn.prepare("SQL")`
- **Entity Definition Style**: SQL strings. Optional `#[derive(rusqlite::types::FromSql)]` for custom type mapping.
  ```rust
  let conn = Connection::open("mydb.sqlite")?;
  conn.execute(
      "CREATE TABLE IF NOT EXISTS notes (
          id      INTEGER PRIMARY KEY,
          title   TEXT NOT NULL,
          body    TEXT,
          created INTEGER NOT NULL
      )",
      [],
  )?;
  let mut stmt = conn.prepare("SELECT id, title, body FROM notes WHERE created > ?1")?;
  ```
- **Extraction Approach**:
  1. Detect `rusqlite` in `Cargo.toml`.
  2. Glob for all `*.rs` files and extract SQL strings from:
     - `conn.execute("SQL", ...)` — first argument
     - `conn.execute_batch("SQL")` — first argument (may contain multiple statements)
     - `conn.prepare("SQL")` — first argument
     - `conn.query_row("SQL", ...)` — first argument
  3. Parse extracted SQL strings for table names.
  4. `conn.execute_batch` may contain `CREATE TABLE` + other DDL; parse all statements in batch.
- **Key Challenges**:
  - Rusqlite maps columns by index (`row.get(0)`) or name (`row.get("column_name")`); index-based access provides no type/name information statically.
  - `Named` params use `?1`, `?2` syntax — these don't affect table extraction.
  - SQLite database files (`.db`, `.sqlite`) co-located in repo can be inspected directly.
- **Analysis Tools**:
  - tree-sitter-rust, regex: `conn\.(execute|prepare|query_row)\s*\(\s*"([^"]+)"`
  - SQLite file inspection for co-located database files
- **Complexity**: Low

## 8. tokio-postgres / postgres Crate

- **Name**: tokio-postgres / postgres
- **Type**: Raw SQL
- **Supported Databases**: PostgreSQL
- **Detection Signals**:
  - `Cargo.toml`: `tokio-postgres = "..."` or `postgres = "..."` in `[dependencies]`
  - Include patterns: `use tokio_postgres::{NoTls, Client}`, `use postgres::{Client, NoTls}`
  - Function usage: `client.query("SQL", ...)`, `client.execute("SQL", ...)`, `client.prepare("SQL")`, `client.batch_execute("SQL")`
- **Entity Definition Style**: Raw SQL strings. `#[derive(tokio_postgres::types::FromSql)]` for custom type mapping.
  ```rust
  let client = tokio_postgres::connect("host=localhost user=postgres dbname=mydb", NoTls).await?;
  let rows = client.query("SELECT id, email, role FROM account WHERE active = $1", &[&true]).await?;
  let email: &str = rows[0].get("email");
  ```
- **Extraction Approach**:
  1. Detect `tokio-postgres` or `postgres` in `Cargo.toml`.
  2. Extract SQL strings from `client.query(`, `client.execute(`, `client.prepare(`, `client.batch_execute(` calls.
  3. Parse SQL strings for table names using a PostgreSQL-dialect parser.
  4. `row.get("column_name")` calls can enumerate accessed columns.
  5. Also scan co-located `*.sql` schema files.
- **Key Challenges**:
  - `$1`, `$2` PostgreSQL placeholders do not affect table extraction.
  - Row column access by index (`row.get(0)`) provides no column name information.
  - Async execution with `tokio` means query strings may be in `async` blocks or closures; tree-sitter handles these fine.
- **Analysis Tools**:
  - tree-sitter-rust, pg_query for PostgreSQL SQL parsing
  - Regex: `client\.(query|execute|prepare)\s*\(\s*"([^"]+)"`
- **Complexity**: Medium

## 9. Rbatis

- **Name**: Rbatis
- **Type**: Relational ORM (async, Rust-native)
- **Supported Databases**: MySQL, PostgreSQL, SQLite, MSSQL
- **Detection Signals**:
  - `Cargo.toml`: `rbatis = "..."`, `rbs = "..."` in `[dependencies]`
  - Include patterns: `use rbatis::*;`, `use rbatis::crud::*`
  - Derive macros: `#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]` combined with `impl_select!`, `impl_insert!`, `impl_update!`, `impl_delete!` macros, or newer `#[crud_table]` / `#[html_sql]` attributes
  - Rbatis v4+: `#[derive(rbatis::rbdc::db::DriverExt)]`, `crud!` macro
- **Entity Definition Style**: Structs with serde derives plus Rbatis CRUD macros.
  ```rust
  #[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
  pub struct BizActivity {
      pub id: Option<String>,
      pub name: Option<String>,
      pub status: Option<i32>,
  }
  crud!(BizActivity {}); // generates CRUD for table "biz_activity"
  // or explicitly:
  impl_select!(BizActivity { select_all() => "SELECT * FROM biz_activity" });
  ```
- **Extraction Approach**:
  1. Detect `rbatis` in `Cargo.toml`.
  2. Search for `crud!(TypeName {})` macro — the type name, converted to snake_case, is the table name.
  3. Search for `impl_select!(TypeName { ... })`, `impl_insert!(TypeName { ... })`, etc. — extract type name.
  4. Search for `#[crud_table(table_name = "explicit_name")]` attributes for explicit table name overrides.
  5. Extract embedded SQL strings within `impl_select!` / `impl_update!` macro bodies for additional table references.
  6. `#[html_sql("SQL")]` or XML mapper files (Rbatis supports MyBatis-style XML mappers) — parse XML `<select>`, `<insert>` elements for SQL.
- **Key Challenges**:
  - Rbatis has gone through major API changes across versions (v2, v3, v4) — macro names differ significantly.
  - XML mapper files (`.xml`) may contain SQL outside of Rust source — glob for `*.xml` files in `src/` or `mapper/` directories.
  - Table name derivation from struct name uses snake_case conversion that may differ from actual table name.
- **Analysis Tools**:
  - tree-sitter-rust for macro invocation parsing
  - XML parser for mapper files
  - Regex: `crud!\s*\(\s*(\w+)` and `#\[crud_table[^\]]*\]`
- **Complexity**: Medium

## 10. Ormx

- **Name**: Ormx
- **Type**: Relational ORM (thin, macro-based)
- **Supported Databases**: PostgreSQL, MySQL
- **Detection Signals**:
  - `Cargo.toml`: `ormx = "..."` in `[dependencies]`
  - Derive macros: `#[derive(ormx::Table)]`
  - Attributes: `#[ormx(table = "table_name", id = field_name, insertable)]`
- **Entity Definition Style**: Struct annotated with `#[derive(ormx::Table)]` and `#[ormx(...)]` attributes.
  ```rust
  #[derive(Debug, ormx::Table)]
  #[ormx(table = "users", id = id, insertable)]
  pub struct User {
      pub id: i32,
      pub email: String,
      #[ormx(default)]
      pub created_at: chrono::DateTime<chrono::Utc>,
  }
  ```
- **Extraction Approach**:
  1. Detect `ormx` in `Cargo.toml`.
  2. Search for `#[derive(ormx::Table)]` or `#[derive(Table)]` (with `use ormx::Table`).
  3. For each struct, extract `#[ormx(table = "name")]` attribute — this is the table name.
  4. Struct fields are column names (respecting `#[ormx(column = "col_name")]` overrides).
  5. `#[ormx(default)]` fields have database-side defaults.
- **Key Challenges**:
  - Ormx is a small library; may be confused with other `Table` derive macros — confirm `ormx` in `Cargo.toml`.
  - `insertable` flag on the macro generates a companion `InsertUser` struct automatically.
- **Analysis Tools**:
  - tree-sitter-rust, regex: `#\[ormx\s*\(\s*table\s*=\s*"([^"]+)"`
- **Complexity**: Low

## 11. SurrealDB Client

- **Name**: SurrealDB (surrealdb crate)
- **Type**: NoSQL / Multi-model Database Client
- **Supported Databases**: SurrealDB
- **Detection Signals**:
  - `Cargo.toml`: `surrealdb = "..."` in `[dependencies]`
  - Include patterns: `use surrealdb::Surreal;`, `use surrealdb::engine::*`
  - Query patterns: `db.query("SurrealQL")`, `db.select("table")`, `db.create("table")`, `db.insert("table")`
  - Derive macros: `#[derive(serde::Serialize, serde::Deserialize)]` on structs used with SurrealDB (no SurrealDB-specific derive, but serde is required)
- **Entity Definition Style**: SurrealQL statements in string literals, or method-based API using table name strings.
  ```rust
  use surrealdb::Surreal;
  use serde::{Deserialize, Serialize};

  #[derive(Debug, Serialize, Deserialize)]
  struct Person {
      name: String,
      age: u8,
  }

  // Method-based:
  let people: Vec<Person> = db.select("person").await?;
  db.create("person").content(Person { name: "Alice".into(), age: 30 }).await?;

  // SurrealQL:
  db.query("SELECT * FROM person WHERE age > $min").bind(("min", 18)).await?;
  db.query("DEFINE TABLE order SCHEMAFULL; DEFINE FIELD total ON order TYPE number;").await?;
  ```
- **Extraction Approach**:
  1. Detect `surrealdb` in `Cargo.toml`.
  2. Extract string arguments from `db.select("table")`, `db.create("table")`, `db.insert("table")`, `db.update("table")`, `db.delete("table")` — these are direct collection/table name references.
  3. Extract SurrealQL strings from `db.query("...")` calls and parse for `FROM <table>`, `CREATE <table>`, `DEFINE TABLE <table>`, `SELECT ... FROM <table>`.
  4. Identify structs used as type parameters in `db.select::<Vec<MyStruct>>("table")` — these map to the table name in the method argument.
  5. `DEFINE TABLE` and `DEFINE FIELD` SurrealQL statements provide explicit schema definitions.
- **Key Challenges**:
  - SurrealDB uses SurrealQL, not standard SQL — requires a SurrealQL-aware parser or custom regex for statement parsing.
  - SurrealDB's multi-model nature means "tables" may be used as document collections, graph nodes, or time-series — context matters.
  - Record IDs (e.g., `person:alice`) embed the table name; these may appear in string literals.
- **Analysis Tools**:
  - tree-sitter-rust for method call parsing
  - Regex: `db\.(select|create|insert|update|delete)\s*\(\s*"([^"]+)"`
  - Custom SurrealQL parser for `DEFINE TABLE`, `SELECT FROM` patterns
- **Complexity**: Medium

## 12. MongoDB (mongodb crate)

- **Name**: MongoDB Rust Driver (mongodb crate)
- **Type**: NoSQL / Document Database Client
- **Supported Databases**: MongoDB
- **Detection Signals**:
  - `Cargo.toml`: `mongodb = "..."` in `[dependencies]`
  - Include patterns: `use mongodb::{Client, Database, Collection}`, `use mongodb::bson::{doc, Document}`
  - Function usage: `db.collection::<T>("name")`, `db.collection("name")`, `client.database("name")`
  - Derive macros: `#[derive(serde::Serialize, serde::Deserialize)]` on document structs; sometimes `#[derive(mongodb::bson::Document)]`
- **Entity Definition Style**: Collection name passed as a string to `db.collection(...)`, with document structure defined by Rust structs using serde.
  ```rust
  use mongodb::bson::doc;
  use serde::{Deserialize, Serialize};

  #[derive(Debug, Serialize, Deserialize)]
  pub struct Order {
      #[serde(rename = "_id", skip_serializing_if = "Option::is_none")]
      pub id: Option<mongodb::bson::oid::ObjectId>,
      pub customer_id: String,
      pub total: f64,
      pub items: Vec<OrderItem>,
  }

  let collection: Collection<Order> = db.collection::<Order>("orders");
  collection.insert_one(order, None).await?;
  collection.find(doc! { "customer_id": &cid }, None).await?;
  ```
- **Extraction Approach**:
  1. Detect `mongodb` in `Cargo.toml`.
  2. Extract collection names from `db.collection::<T>("name")` and `db.collection("name")` — the string argument is the collection name.
  3. Extract the type parameter `T` from typed collection calls (`collection::<Order>(...)`) — this struct defines the document schema.
  4. For the identified struct types, extract field names (considering `#[serde(rename = "...")]` attributes for actual field names in MongoDB).
  5. `doc! { "field": value }` query literals reveal field names used in queries.
  6. `client.database("name")` reveals the database name (not collection).
- **Key Challenges**:
  - Collection names may be stored in configuration or environment variables, not string literals.
  - MongoDB is schema-less; structs define the application-side shape but the collection itself has no enforced schema.
  - `#[serde(rename = "...")]` attributes change field names between Rust and MongoDB; must parse these for accurate column/field names.
  - Aggregation pipelines use `doc!` with field names — useful for field discovery but complex to parse.
- **Analysis Tools**:
  - tree-sitter-rust: parse type-parameterized method calls, serde attribute macros
  - Regex: `db\.collection:?:?<\w+>?\s*\(\s*"([^"]+)"`
- **Complexity**: Medium

## 13. Redis (redis-rs)

- **Name**: redis-rs
- **Type**: Key-Value Store Client
- **Supported Databases**: Redis
- **Detection Signals**:
  - `Cargo.toml`: `redis = "..."` in `[dependencies]`
  - Include patterns: `use redis::{Client, Commands, Connection, AsyncCommands}`
  - Function usage: `redis::cmd("HSET")`, `con.set("key", value)`, `con.hset("hash", "field", value)`, `con.get("key")`
- **Entity Definition Style**: No formal entity definition. Key naming conventions define logical entities. Hash keys (HSET/HGET) represent struct-like entities.
  ```rust
  use redis::Commands;
  // Key-value (no schema):
  let _: () = con.set("session:42:token", &token)?;
  // Hash (struct-like entity):
  con.hset_multiple("user:42", &[("name", &name), ("email", &email)])?;
  // Sorted set (list entity):
  con.zadd("leaderboard:global", score, &user_id)?;
  ```
- **Extraction Approach**:
  1. Detect `redis` in `Cargo.toml`.
  2. Extract key name string literals from Redis command calls.
  3. Identify key naming patterns (e.g., `"entity_type:id:field"`, `"entity_type:id"`) to infer logical entity types.
  4. `HSET` / `HGET` / `HMSET` / `HGETALL` operations on a hash key indicate a struct-like entity; the hash key prefix (before `:`) is the entity type.
  5. `ZADD` / `ZRANGE` on sorted set keys indicate list/ranking entities.
  6. Look for constants or enums defining key prefixes as authoritative entity name sources.
- **Key Challenges**:
  - Redis has no schema; entities are entirely implicit in key naming conventions.
  - Key names with dynamic parts (`user:{id}`) make static extraction partial — extract the static prefix.
  - Lua scripts embedded as strings may contain Redis commands.
  - `redis::Script` contains Lua — parse Lua for `redis.call("HSET", ...)` patterns.
- **Analysis Tools**:
  - tree-sitter-rust, regex
  - Pattern analysis for key name conventions
- **Complexity**: High

## 14. Elasticsearch (elasticsearch crate)

- **Name**: elasticsearch (official Rust client)
- **Type**: Search Engine / Document Store Client
- **Supported Databases**: Elasticsearch, OpenSearch
- **Detection Signals**:
  - `Cargo.toml`: `elasticsearch = "..."` in `[dependencies]`
  - Include patterns: `use elasticsearch::{Elasticsearch, IndexParts, SearchParts}`
  - Function usage: `client.index(IndexParts::Index("name"))`, `client.search(SearchParts::Index(&["name"]))`, `client.indices().create(IndicesParts::Index("name"))`
- **Entity Definition Style**: Index names passed as string arguments to API calls. Document structure defined by serde structs.
  ```rust
  use elasticsearch::{IndexParts, SearchParts};

  #[derive(serde::Serialize, serde::Deserialize)]
  struct Product {
      id: u64,
      name: String,
      price: f64,
      tags: Vec<String>,
  }

  client.index(IndexParts::Index("products"))
      .body(product)
      .send()
      .await?;
  client.search(SearchParts::Index(&["products"]))
      .body(json!({ "query": { "match": { "name": query } } }))
      .send()
      .await?;
  ```
- **Extraction Approach**:
  1. Detect `elasticsearch` in `Cargo.toml`.
  2. Extract index names from `IndexParts::Index("name")`, `SearchParts::Index(&["name"])`, `IndicesParts::Index("name")`.
  3. Identify document struct types used as `.body(struct)` arguments.
  4. Extract field names from those structs (respecting `#[serde(rename)]`).
  5. Mapping definition JSON passed to `client.indices().create(...).body(mapping_json)` contains explicit field type definitions — parse if available as string literals.
- **Key Challenges**:
  - Index names may be dynamically constructed (e.g., date-based indices like `"logs-2024-01"`).
  - Elasticsearch mappings are JSON, not Rust code — parse JSON mapping bodies for field definitions.
  - OpenSearch uses the same client pattern; detection is identical.
- **Analysis Tools**:
  - tree-sitter-rust, regex: `IndexParts::Index\s*\(\s*"([^"]+)"\s*\)`
  - JSON parser for mapping bodies
- **Complexity**: Medium

## 15. Refinery Migration Tool

- **Name**: refinery
- **Type**: Migration Tool
- **Supported Databases**: PostgreSQL, MySQL, SQLite, MSSQL (via tokio-postgres, mysql, rusqlite, tiberius)
- **Detection Signals**:
  - `Cargo.toml`: `refinery = "..."`, `refinery-core` in `[dependencies]`
  - Migration patterns:
    - SQL files: `migrations/V<VERSION>__<description>.sql` (Flyway-compatible naming)
    - Rust module migrations: `migrations/V<VERSION>__<name>.rs` (Rust migration functions)
  - Macro: `refinery::embed_migrations!("migrations")` in Rust source
  - Config: `refinery.toml` (optional)
- **Entity Definition Style**: SQL DDL in versioned `.sql` files or Rust code in `.rs` files.
  ```sql
  -- migrations/V1__create_products.sql
  CREATE TABLE products (
      id BIGSERIAL PRIMARY KEY,
      sku TEXT NOT NULL UNIQUE,
      name TEXT NOT NULL,
      price NUMERIC(10, 2)
  );
  ```
- **Extraction Approach**:
  1. Detect `refinery` in `Cargo.toml`.
  2. Locate `migrations/` directory; look for `V<NUMBER>__<name>.sql` files.
  3. Sort by version number, process `up` SQL (refinery does not use `.down.sql` by default — migrations are generally irreversible).
  4. Parse `CREATE TABLE` and `ALTER TABLE` statements to reconstruct schema.
  5. For Rust-based migrations (`.rs` files), parse the `migrate()` function body for SQL strings or SeaQuery DSL.
- **Key Challenges**:
  - Refinery uses Flyway naming convention (`V<N>__description`) which differs from SQLx/Diesel conventions.
  - Rust-based migrations require parsing Rust code for SQL strings.
- **Analysis Tools**:
  - Glob + sort for migration file discovery
  - SQL parser for `.sql` migration files
  - tree-sitter-rust for `.rs` migration files
- **Complexity**: Low

## 16. Prisma Rust Client (schema.prisma)

- **Name**: Prisma Client Rust (prisma-client-rust)
- **Type**: Relational ORM (code-generated client)
- **Supported Databases**: PostgreSQL, MySQL, SQLite, MongoDB, SQL Server, CockroachDB
- **Detection Signals**:
  - `Cargo.toml`: `prisma-client-rust = "..."`, `prisma-client-rust-cli` in build dependencies
  - File: `prisma/schema.prisma` (the primary schema file — always present)
  - Config: `prisma/schema.prisma` contains `generator client { provider = "prisma-client-rust" }`
  - Generated code: `src/prisma.rs` or `prisma/mod.rs` (generated by `cargo prisma generate`)
- **Entity Definition Style**: Prisma Schema Language (PSL) in `schema.prisma`.
  ```prisma
  generator client {
    provider = "prisma-client-rust"
    output   = "src/prisma.rs"
  }

  datasource db {
    provider = "postgresql"
    url      = env("DATABASE_URL")
  }

  model User {
    id        Int      @id @default(autoincrement())
    email     String   @unique
    name      String?
    posts     Post[]
    createdAt DateTime @default(now())
  }

  model Post {
    id        Int    @id @default(autoincrement())
    title     String
    content   String?
    authorId  Int
    author    User   @relation(fields: [authorId], references: [id])
  }
  ```
- **Extraction Approach**:
  1. Detect `prisma/schema.prisma` file (this is the primary signal — Prisma always requires it).
  2. Detect `prisma-client-rust` in `Cargo.toml`.
  3. Parse `schema.prisma` for `model ModelName { ... }` blocks — each model maps directly to a database table.
  4. Extract field names, types, and attributes (`@id`, `@unique`, `@default`, `@relation`) from each model block.
  5. `@@map("actual_table_name")` attribute overrides the table name — capture this if present.
  6. `datasource db { provider = "..." }` reveals the database type.
  7. Optionally parse the generated `src/prisma.rs` for additional confirmation.
- **Key Challenges**:
  - `schema.prisma` is always the source of truth; generated Rust code is derived from it.
  - `@relation` fields are virtual and do not map to columns directly; differentiate from regular fields.
  - Prisma supports MongoDB (`@db.ObjectId`), which changes entity semantics from relational to document.
  - `enum` in Prisma maps to a database enum type, not a table.
- **Analysis Tools**:
  - Regex: `^model\s+(\w+)\s*\{` for model extraction from `schema.prisma`
  - Custom PSL parser (Prisma's schema format is well-documented and relatively simple to parse)
  - tree-sitter grammar for Prisma exists in community
- **Complexity**: Low

## 17. prost (Protocol Buffers for Rust)

- **Name**: prost
- **Type**: Schema File / Serialization Framework
- **Supported Databases**: N/A (serialization format)
- **Detection Signals**:
  - `Cargo.toml`: `prost = "..."`, `prost-types = "..."`, `tonic = "..."` (gRPC, implies prost)
  - Build dependencies: `prost-build = "..."` in `[build-dependencies]`, `build.rs` with `prost_build::compile_protos(...)`
  - File extensions: `*.proto`
  - Generated include: `include!(concat!(env!("OUT_DIR"), "/mynamespace.rs"))` in Rust source
  - Derive macros on generated structs: `#[derive(Clone, PartialEq, prost::Message)]`
- **Entity Definition Style**: `.proto` message definitions compiled to Rust structs via `prost-build`.
  ```proto
  syntax = "proto3";
  package myservice;

  message UserProfile {
    uint64 user_id = 1;
    string display_name = 2;
    string avatar_url = 3;
    repeated string roles = 4;
  }
  ```
  Generated Rust:
  ```rust
  #[derive(Clone, PartialEq, ::prost::Message)]
  pub struct UserProfile {
      #[prost(uint64, tag = "1")]
      pub user_id: u64,
      #[prost(string, tag = "2")]
      pub display_name: ::prost::alloc::string::String,
      // ...
  }
  ```
- **Extraction Approach**:
  1. Detect `prost` or `tonic` in `Cargo.toml`.
  2. Glob for all `*.proto` files.
  3. Parse `message MessageName { ... }` blocks for entity candidates.
  4. Cross-reference with SQL/NoSQL storage calls — if a prost message type is serialized to a blob column or stored in a cache, it is a persisted entity.
  5. `build.rs` with `prost_build::compile_protos` lists the exact `.proto` files being compiled — use this to prioritize which `.proto` files are in scope.
- **Key Challenges**: Same as all Protobuf approaches — distinguishing persisted messages from wire-format-only messages.
- **Analysis Tools**:
  - Regex: `^message\s+(\w+)\s*\{`
  - `build.rs` parsing to identify which `.proto` files are compiled
- **Complexity**: Medium

## 18. serde Serialize/Deserialize as Entity Signal (Heuristic)

- **Name**: serde derives as Entity Heuristic
- **Type**: Heuristic Entity Signal
- **Supported Databases**: Any
- **Detection Signals**:
  - `Cargo.toml`: `serde = { version = "...", features = ["derive"] }`
  - Derive macros: `#[derive(serde::Serialize, serde::Deserialize)]` or `#[derive(Serialize, Deserialize)]`
  - Struct file location: `src/models/`, `src/entities/`, `src/domain/`, `src/db/`, `src/schema/`
  - Field patterns: `id` / `*_id` fields, `created_at`, `updated_at`, `deleted_at` (soft delete), `#[serde(rename = "...")]` attributes
  - Struct used as type parameter in database calls (MongoDB, SQLx, etc.)
- **Entity Definition Style**: Plain Rust structs with serde derives.
  ```rust
  #[derive(Debug, Clone, Serialize, Deserialize)]
  pub struct Invoice {
      pub id: uuid::Uuid,
      pub customer_id: uuid::Uuid,
      pub line_items: Vec<LineItem>,
      pub total_cents: i64,
      pub created_at: chrono::DateTime<chrono::Utc>,
      pub paid_at: Option<chrono::DateTime<chrono::Utc>>,
  }
  ```
- **Extraction Approach**:
  1. This is a supplementary heuristic — apply after exhausting framework-specific signals.
  2. Find all structs with `#[derive(...Serialize..., ...Deserialize...)]`.
  3. Score each struct:
     - Located in `models/`, `entities/`, `domain/`, `db/` directory (+3 points)
     - Has an `id` field of type `i32`, `i64`, `u64`, `Uuid` (+2 points)
     - Has `created_at` or `updated_at` field (+1 each)
     - Has `deleted_at: Option<...>` field (+2 points — soft delete pattern)
     - Used as type parameter in a confirmed database call (+4 points)
     - Struct name is a singular noun (common entity naming) (+1 point)
  4. Structs scoring >= 5 are candidate entities.
  5. Field names should respect `#[serde(rename = "...")]` for actual storage field names.
- **Key Challenges**:
  - Many Rust structs use serde for JSON APIs, configuration, or inter-service communication, not database storage.
  - False positives are significant without cross-referencing with database library usage.
  - `#[serde(skip)]` fields are not persisted; filter these out.
  - `#[serde(flatten)]` embeds another struct's fields — requires recursive resolution.
- **Analysis Tools**:
  - tree-sitter-rust: parse derive attributes, struct field definitions, serde attributes
  - Regex: `#\[derive\([^\]]*(?:Serialize|Deserialize)[^\]]*\)\]`
- **Complexity**: High

## Repository Detection Plan

### Step 1: Cargo.toml Analysis (Primary Signal)
- Read the root `Cargo.toml` and all workspace member `Cargo.toml` files
- Extract `[dependencies]` and `[dev-dependencies]` sections
- Build a map of: database library → detected (true/false)

Key dependency → framework mapping:

| Cargo.toml Key | Framework |
|---|---|
| `diesel` | Diesel ORM |
| `diesel_migrations` | Diesel Migrations |
| `sqlx` | SQLx |
| `sea-orm` | SeaORM |
| `sea-orm-migration` | SeaORM Migrations |
| `rusqlite` | Rusqlite |
| `tokio-postgres` | tokio-postgres |
| `postgres` | postgres crate |
| `rbatis` | Rbatis |
| `ormx` | Ormx |
| `surrealdb` | SurrealDB |
| `mongodb` | MongoDB |
| `redis` | redis-rs |
| `elasticsearch` | Elasticsearch |
| `refinery` | Refinery |
| `prisma-client-rust` | Prisma Client Rust |
| `prost` | prost (Protobuf) |
| `tonic` | tonic (implies prost) |
| `flatbuffers` | FlatBuffers |

### Step 2: File Pattern Detection
Run in parallel with Step 1:

- Check for `prisma/schema.prisma` (Prisma — always present if Prisma is used)
- Check for `src/schema.rs` with `diesel::table!` macro (Diesel schema)
- Check for `diesel.toml` (Diesel config)
- Check for `migrations/` directory (SQLx, Diesel, Refinery, SeaORM migrations)
- Check for `migration/src/*.rs` (SeaORM migration modules)
- Check for `*.proto` files (prost / gRPC)
- Check for `*.fbs` files (FlatBuffers)
- Check for `.sqlx/` directory or `sqlx-data.json` (SQLx offline mode cache)

### Step 3: Framework-Specific Entity Extraction
Apply extraction strategies in priority order (higher confidence first):

**High Confidence (Schema Files / Declarative Annotations):**
1. **Prisma**: Parse `prisma/schema.prisma` for `model` blocks
2. **Diesel**: Parse `src/schema.rs` for `diesel::table!` macros; parse `#[diesel(table_name)]` on structs
3. **SeaORM**: Parse `#[derive(DeriveEntityModel)]` structs with `#[sea_orm(table_name)]`
4. **SeaORM Migrations**: Parse `#[derive(Iden)]` enums in migration files + `Table::create()` calls
5. **Ormx**: Parse `#[derive(ormx::Table)]` with `#[ormx(table = "...")]`
6. **Rbatis**: Parse `crud!(TypeName)` macro invocations
7. **Protobuf/FlatBuffers**: Parse `*.proto` / `*.fbs` schema files

**Medium Confidence (SQL Strings in Typed Contexts):**
8. **SQLx `query_as!`**: Extract SQL from `query_as!(Type, "SQL")` macros + `.sqlx/*.json` cache
9. **SQLx migrations**: Process migration files in version order
10. **Diesel migrations**: Process `migrations/*/up.sql` in chronological order
11. **Refinery**: Process `migrations/V*__*.sql` in version order
12. **tokio-postgres / postgres**: Extract SQL strings from `client.query(`, `client.execute(`
13. **Rusqlite**: Extract SQL strings from `conn.execute(`, `conn.prepare(`, `conn.query_row(`
14. **MongoDB**: Extract collection names from `db.collection::<T>("name")`
15. **SurrealDB**: Extract table names from `db.select("table")`, `db.create("table")`
16. **Elasticsearch**: Extract index names from `IndexParts::Index("name")`

**Lower Confidence (Heuristic):**
17. **serde heuristic**: Score all serde-derived structs by entity likelihood
18. **Redis key patterns**: Extract key prefix patterns from Redis command strings

### Step 4: SQL String Aggregation
For all frameworks that use raw SQL strings:
1. Apply SQL parser (sqlparser-rs for multi-dialect, pg_query for PostgreSQL-specific)
2. Extract table names from `CREATE TABLE`, `FROM`, `INTO`, `UPDATE`, `JOIN ... ON`, `INSERT INTO`
3. Deduplicate, normalize case
4. Rank by frequency of appearance across the codebase

### Step 5: Cross-Reference and Confidence Scoring
- Merge all entity candidates from all frameworks
- Assign confidence:
  - Found in schema file (`schema.rs`, `schema.prisma`, `*.proto`, `*.fbs`): **High**
  - Found in migration `CREATE TABLE`: **High**
  - Found in typed ORM annotation (`#[diesel(table_name)]`, `#[sea_orm(table_name)]`): **High**
  - Found in SQL `query_as!` macro: **High**
  - Found in SQL `FROM`/`INTO`/`UPDATE` strings: **Medium**
  - Found via serde heuristic scoring: **Low**
- Cross-reference: if a struct found via serde heuristic also appears as a type parameter in a confirmed DB call, upgrade confidence to **Medium**

### Step 6: Relationship Mapping
- Parse `diesel::joinable!()` macros for FK relationships
- Parse `#[sea_orm(has_many)]`, `#[sea_orm(belongs_to)]` for SeaORM relationships
- Parse `@relation` in Prisma models
- Parse `Relation` enum variants in SeaORM entities

### Step 7: Output
- Produce entity list:
  - Entity name
  - Table / collection / index name (authoritative vs. inferred)
  - Database type (relational, document, key-value, search)
  - Framework detected
  - Confidence level (High / Medium / Low)
  - Source file locations
  - Field list (if extractable)
- Separate into: confirmed entities (High confidence), probable entities (Medium), candidates (Low)
- Flag entities found only in schema/migration files but not referenced in application code as "possibly legacy"
