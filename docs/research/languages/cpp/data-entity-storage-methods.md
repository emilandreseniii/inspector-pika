# C++ Data Entity Storage Methods

Catalog of significant data entity storage frameworks, libraries, and approaches for C++ repositories. Intended to support automated static analysis for extracting data entities (database tables, document collections, etc.).

---

## 1. ODB ORM

- **Name**: ODB ORM
- **Type**: Relational ORM
- **Supported Databases**: PostgreSQL, MySQL, SQLite, Oracle, MS SQL Server
- **Detection Signals**:
  - Dependencies: `odb`, `libodb`, `libodb-pgsql`, `libodb-mysql`, `libodb-sqlite` in `vcpkg.json`, `conanfile.txt`, or `CMakeLists.txt` (`find_package(ODB ...)`, `target_link_libraries(... odb odb-pgsql ...)`)
  - Include patterns: `#include <odb/core.hxx>`, `#include <odb/database.hxx>`, `#include <odb/pgsql/database.hxx>`
  - File extensions: `*.hxx` (ODB-annotated header files), `*-odb.hxx`, `*-odb.cxx` (generated files), `*.sql` (generated schema)
  - Config files: none specific, but `CMakeLists.txt` often invokes `odb` compiler via `add_custom_command`
- **Entity Definition Style**: C++ class/struct annotated with `#pragma db` directives inside header files. The ODB compiler pre-processes these headers to generate mapping code.
  ```cpp
  #pragma db object
  class Person {
  public:
    #pragma db id auto
    unsigned long id_;
    std::string first_;
    std::string last_;
  };
  ```
- **Extraction Approach**:
  1. Scan all `*.hxx`, `*.h`, `*.hpp` files for `#pragma db object` or `#pragma db view`.
  2. For each file containing these pragmas, parse class/struct declarations that follow `#pragma db object`.
  3. The class name maps directly to the table name (or use `#pragma db table("name")` override — capture that value).
  4. Within each entity class, collect member variables annotated with `#pragma db column`, `#pragma db id`, `#pragma db transient` (skip transient members).
  5. Optionally scan generated `*-odb.hxx` files for `CREATE TABLE` statements to confirm schema.
  6. Also scan `*-odb.sql` or `*.sql` files generated by `odb --generate-schema` for `CREATE TABLE` DDL.
- **Key Challenges**:
  - ODB uses a non-standard pragma syntax that most generic C++ parsers will not understand natively; requires custom handling.
  - Inheritance hierarchies (`#pragma db object polymorphic`) spread entity definitions across parent/child classes.
  - Composite value types (`#pragma db value`) are not tables themselves but are embedded.
  - Template-based containers (`std::vector<T>`) in entities generate separate join tables.
  - The ODB compiler must be run before build, so generated files may or may not be present in the repo.
- **Analysis Tools**:
  - tree-sitter-cpp: parse class declarations and extract pragma comments as annotation nodes
  - libclang / clang-ast-dump: parse headers and walk AST for `PragmaComment` nodes (requires full compilation environment)
  - Regex fallback: `#pragma\s+db\s+object` followed by `class\s+(\w+)`
- **Complexity**: High

## 2. SOCI

- **Name**: SOCI
- **Type**: Raw SQL / Struct Binding
- **Supported Databases**: PostgreSQL, MySQL, SQLite, Oracle, DB2, Firebird, ODBC
- **Detection Signals**:
  - Dependencies: `soci` in `vcpkg.json` (`"soci"`), `conanfile.txt` (`soci/4.x.x`), `CMakeLists.txt` (`find_package(SOCI ...)` or `target_link_libraries(... soci_core soci_postgresql ...)`)
  - Include patterns: `#include <soci/soci.h>`, `#include <soci/postgresql/soci-postgresql.h>`
  - No dedicated entity definition files; entities defined inline via SQL strings
- **Entity Definition Style**: SQL strings embedded in C++ code; optional `type_conversion<T>` specializations that map struct fields to SQL columns.
  ```cpp
  soci::session sql("postgresql://...");
  sql << "SELECT id, name FROM users WHERE id = :id", soci::into(u), soci::use(id);
  // type_conversion specialization:
  template<> struct soci::type_conversion<User> {
    static void from_base(soci::values const& v, soci::indicator, User& u) {
      u.id = v.get<int>("id");
      u.name = v.get<std::string>("name");
    }
  };
  ```
- **Extraction Approach**:
  1. Search all `*.cpp`, `*.cxx`, `*.cc` files for `soci::session` instantiations to confirm SOCI usage.
  2. Extract SQL string literals passed to `<<` operator or `prepare` calls using regex: `"(SELECT|INSERT|UPDATE|DELETE|CREATE TABLE)[^"]*"` (handle multi-line raw strings).
  3. Parse SQL strings for table names: `FROM\s+(\w+)`, `INTO\s+(\w+)`, `UPDATE\s+(\w+)`, `CREATE TABLE\s+(\w+)`.
  4. Search for `soci::type_conversion<(\w+)>` specializations to map C++ types to SQL tables.
  5. Supplement with DDL SQL files in the project directory.
- **Key Challenges**:
  - SQL strings may be constructed dynamically (string concatenation, format strings) making static extraction incomplete.
  - No formal entity annotation; table names only appear in SQL strings.
  - `type_conversion` specializations may be in separate header files not obviously connected to the SQL usage.
- **Analysis Tools**:
  - tree-sitter-cpp: locate string literals and `<<` expressions
  - Regex on raw source text for SQL keyword extraction
  - SQLite/PostgreSQL SQL parsers (pg_query, sqlparser-rs bindings) to parse extracted SQL strings
- **Complexity**: Medium

## 3. SQLAPI++

- **Name**: SQLAPI++
- **Type**: Raw SQL / Query Builder
- **Supported Databases**: Oracle, SQL Server, DB2, Sybase, Informix, InterBase, SQLBase, MySQL, PostgreSQL, SQLite, SQL Anywhere
- **Detection Signals**:
  - Dependencies: `sqlapi` or `SQLAPI` in `vcpkg.json`, `conanfile.txt`, or manual lib paths in `CMakeLists.txt`
  - Include patterns: `#include <SQLAPI.h>`
  - No dedicated entity files; purely SQL string-driven
- **Entity Definition Style**: Pure SQL strings passed to `SACommand` objects.
  ```cpp
  SACommand cmd(&con, "SELECT user_id, email FROM accounts WHERE active = :1");
  ```
- **Extraction Approach**:
  1. Detect `#include <SQLAPI.h>` or `SAConnection`, `SACommand` usage.
  2. Extract all string literals passed to `SACommand` constructor or `setCommandText`.
  3. Apply SQL parsing to extract table names from those strings.
  4. Scan co-located SQL migration/schema files.
- **Key Challenges**:
  - No structured entity definitions at all; entities are purely implicit in SQL strings.
  - Dynamic SQL construction severely limits static analysis.
- **Analysis Tools**:
  - tree-sitter-cpp for AST-based string literal extraction
  - Regex for `SACommand\s*\w*\s*\([^,]+,\s*"([^"]+)"` patterns
- **Complexity**: Medium

## 4. Qt SQL Module

- **Name**: Qt SQL (QSqlTableModel, QSqlRelationalTableModel, QSqlQuery)
- **Type**: Relational ORM / Query Builder
- **Supported Databases**: SQLite, PostgreSQL, MySQL/MariaDB, ODBC, Oracle (via plugins)
- **Detection Signals**:
  - Dependencies: `Qt5::Sql` or `Qt6::Sql` in `CMakeLists.txt` (`target_link_libraries(... Qt5::Sql ...)`); `QT += sql` in `.pro` files
  - Include patterns: `#include <QSqlDatabase>`, `#include <QSqlTableModel>`, `#include <QSqlRelationalTableModel>`, `#include <QSqlQuery>`, `#include <QtSql/QtSql>`
  - File extensions: `.ui` files may reference SQL models indirectly; `.pro` files for qmake builds
- **Entity Definition Style**: Table names passed as strings to model `setTable()` calls, or SQL strings in `QSqlQuery::exec()`.
  ```cpp
  QSqlTableModel model;
  model.setTable("employees");
  model.select();
  // or raw:
  QSqlQuery query;
  query.exec("SELECT id, name FROM departments");
  ```
- **Extraction Approach**:
  1. Search for `QSqlTableModel` and `QSqlRelationalTableModel` class instantiations.
  2. Extract string arguments to `.setTable("...")` calls — these are direct table name references.
  3. For `QSqlQuery` and `QSqlQueryModel`, extract SQL string literals as in the SOCI approach.
  4. Also check `QSqlRelationalTableModel::setRelation()` calls for referenced table names.
  5. Parse `.pro` files to confirm Qt SQL module usage.
- **Key Challenges**:
  - Table names in `setTable()` may be stored in variables rather than literal strings.
  - Qt's signal/slot mechanism and runtime table switching can obscure which tables are accessed.
  - QML-based UIs may use `SqlQueryModel` in JavaScript/QML files — extend scan to `*.qml`.
- **Analysis Tools**:
  - tree-sitter-cpp: match `MethodCallExpression` for `setTable`, `exec`, `prepare`
  - tree-sitter for QML files if QML is present
  - Regex: `setTable\s*\(\s*"([^"]+)"\s*\)`
- **Complexity**: Medium

## 5. Poco Data

- **Name**: Poco::Data (Poco C++ Libraries)
- **Type**: Raw SQL / Struct Binding
- **Supported Databases**: SQLite, MySQL, PostgreSQL, ODBC
- **Detection Signals**:
  - Dependencies: `poco` in `vcpkg.json`, `conanfile.txt` (`poco/1.x.x`), `CMakeLists.txt` (`find_package(Poco REQUIRED Data DataSQLite DataMySQL ...)`)
  - Include patterns: `#include <Poco/Data/Session.h>`, `#include <Poco/Data/SQLite/Connector.h>`, `#include "Poco/Data/MySQL/Connector.h"`
  - Poco Data uses `<<` streaming syntax similar to SOCI
- **Entity Definition Style**: SQL strings passed via the `<<` streaming operator to a `Session`. Struct binding via `Poco::Data::Keywords::use()` and `into()`.
  ```cpp
  Poco::Data::Session ses("SQLite", "sample.db");
  ses << "SELECT name, age FROM People", into(names), into(ages), now;
  ```
- **Extraction Approach**:
  1. Detect `Poco::Data::Session` instantiations.
  2. Extract string literals streamed via `<<` for SQL parsing.
  3. Parse those strings for `FROM`, `INTO`, `UPDATE`, `CREATE TABLE` table name patterns.
  4. Examine `Poco::Data::TypeHandler<T>` specializations (similar to SOCI `type_conversion`) for struct-to-table mappings.
- **Key Challenges**:
  - SQL is embedded directly in C++ streaming expressions; multi-line strings are common.
  - No declarative entity annotation; only implicit in SQL strings.
- **Analysis Tools**:
  - tree-sitter-cpp for streaming expression parsing
  - Regex for `ses\s*<<\s*"([^"]*)"` extraction
- **Complexity**: Medium

## 6. Wt::Dbo

- **Name**: Wt::Dbo (Witty C++ Web Framework ORM)
- **Type**: Relational ORM
- **Supported Databases**: PostgreSQL, MySQL, SQLite, Firebird
- **Detection Signals**:
  - Dependencies: `wt` in `vcpkg.json`, `conanfile.txt` (`wt/4.x.x`), `CMakeLists.txt` (`find_package(Wt REQUIRED ...)`); link to `wtdbo`, `wtdbosqlite3`, `wtdbopostgres`
  - Include patterns: `#include <Wt/Dbo/Dbo.h>`, `#include <Wt/Dbo/Session.h>`, `#include <Wt/Dbo/backend/Sqlite3.h>`
- **Entity Definition Style**: Structs/classes with a `persist` template method that enumerates fields. The class name (by convention) maps to the table name.
  ```cpp
  class User {
  public:
    std::string name;
    std::string email;
    template<class Action>
    void persist(Action& a) {
      dbo::field(a, name, "name");
      dbo::field(a, email, "email");
    }
  };
  // Registration:
  session.mapClass<User>("user");
  ```
- **Extraction Approach**:
  1. Scan all headers and source files for `dbo::field(` and `persist(Action& a)` method definitions.
  2. Collect the class name of each type that implements the `persist` template method.
  3. Search for `session.mapClass<ClassName>("table_name")` calls — the string argument is the authoritative table name.
  4. Fall back to class name (lowercased) if no `mapClass` call is found.
  5. Within `persist` methods, extract `dbo::field(a, member, "column_name")` calls for column enumeration.
- **Key Challenges**:
  - `persist` is a template method; its instantiation is deferred until `mapClass` is called, so full field enumeration may require following template instantiation logic.
  - Collection fields (`dbo::hasMany`, `dbo::belongsTo`) create foreign key relationships rather than additional entity tables.
- **Analysis Tools**:
  - tree-sitter-cpp: parse template method definitions and method call expressions
  - Regex: `session\.mapClass<(\w+)>\s*\(\s*"([^"]+)"\s*\)`
- **Complexity**: High

## 7. Raw libpq (PostgreSQL C++ Connector)

- **Name**: libpq (PostgreSQL official C library, used from C++)
- **Type**: Raw SQL
- **Supported Databases**: PostgreSQL
- **Detection Signals**:
  - Dependencies: `libpq` in `vcpkg.json`, `CMakeLists.txt` (`find_package(PostgreSQL REQUIRED)`, `target_link_libraries(... PostgreSQL::PostgreSQL ...)`)
  - Include patterns: `#include <libpq-fe.h>`, `#include <postgresql/libpq-fe.h>`
  - Function usage: `PQconnectdb`, `PQexec`, `PQexecParams`, `PQprepare`
- **Entity Definition Style**: SQL strings passed to `PQexec` or `PQexecParams`.
- **Extraction Approach**:
  1. Detect `#include <libpq-fe.h>` or `PQconnectdb` calls.
  2. Extract all string literals passed to `PQexec(conn, "...")` and `PQexecParams`.
  3. Parse SQL strings for table names.
  4. Also scan co-located `*.sql` DDL schema files.
- **Key Challenges**: Fully dynamic SQL; string building common; stored procedures may define entities outside the application code.
- **Analysis Tools**: tree-sitter-cpp, regex for `PQexec\s*\([^,]+,\s*"([^"]+)"`
- **Complexity**: Medium

## 9. SQLiteCpp

- **Name**: SQLiteCpp
- **Type**: Raw SQL / Thin C++ Wrapper
- **Supported Databases**: SQLite
- **Detection Signals**:
  - Dependencies: `sqlitecpp` in `vcpkg.json` (`"sqlitecpp"`), `CMakeLists.txt` (`add_subdirectory(SQLiteCpp)`, `target_link_libraries(... SQLiteCpp ...)`)
  - Include patterns: `#include <SQLiteCpp/SQLiteCpp.h>`, `#include "SQLiteCpp/Database.h"`
  - Function usage: `SQLite::Database`, `SQLite::Statement`, `db.exec(`, `SQLite::Transaction`
- **Entity Definition Style**: SQL strings.
  ```cpp
  SQLite::Database db("example.db");
  db.exec("CREATE TABLE IF NOT EXISTS users (id INTEGER, name TEXT)");
  SQLite::Statement query(db, "SELECT id, name FROM users");
  ```
- **Extraction Approach**:
  1. Detect `SQLite::Database` instantiation.
  2. Extract string literals passed to `db.exec()`, `SQLite::Statement` constructor, `db.execAndGet()`.
  3. Parse SQL strings for table names and `CREATE TABLE` definitions.
  4. SQLite `.db` or `.sqlite` files co-located in repo can be opened and inspected for schema.
- **Key Challenges**: Database file may be created at runtime with schema defined dynamically.
- **Analysis Tools**: tree-sitter-cpp, regex, SQLite file inspection (`.schema` pragma)
- **Complexity**: Low

## 11. ORMPP

- **Name**: ORMPP
- **Type**: Relational ORM
- **Supported Databases**: MySQL, PostgreSQL, SQLite
- **Detection Signals**:
  - Dependencies: header-only, typically vendored; `ormpp` directory in repo or `#include "ormpp/dbng.hpp"`
  - Include patterns: `#include "ormpp/dbng.hpp"`, `#include <ormpp/dbng.hpp>`
  - Usage: `ormpp::dbng<ormpp::sqlite>`, `REGISTER_AUTO_KEY`, `REFLECTION` macros
- **Entity Definition Style**: Plain structs annotated with `REFLECTION` macro to enumerate fields, plus `REGISTER_AUTO_KEY` for primary keys.
  ```cpp
  struct Person {
    int id;
    std::string name;
    int age;
  };
  REFLECTION(Person, id, name, age)
  REGISTER_AUTO_KEY(Person, id)
  // Usage:
  db.create_datatable<Person>();
  db.insert(person);
  ```
- **Extraction Approach**:
  1. Search for `REFLECTION(TypeName, ...)` macro invocations — the first argument is the entity type/table name.
  2. Collect all struct definitions matching those type names.
  3. `REGISTER_AUTO_KEY(TypeName, field)` confirms a type is an ORM entity.
  4. `db.create_datatable<TypeName>()` calls also signal entity types via template argument.
- **Key Challenges**: Header-only and often vendored; may need to detect by macro name rather than package manager dependency.
- **Analysis Tools**: tree-sitter-cpp (macro expansion patterns), regex: `REFLECTION\s*\(\s*(\w+)`
- **Complexity**: Medium

## 12. Hiberlite

- **Name**: Hiberlite
- **Type**: Relational ORM (SQLite-focused)
- **Supported Databases**: SQLite
- **Detection Signals**:
  - Dependencies: typically built as a static lib or vendored; `hiberlite` in `CMakeLists.txt` or subdirectory
  - Include patterns: `#include "hiberlite.h"`, `#include <hiberlite/hiberlite.h>`
  - Usage: `hiberlite::Database db`, `db.registerBeanClass<T>()`, `HIBERLITE_EXPORT` macro
- **Entity Definition Style**: Structs/classes with a `hibernate` template method enumerating fields (similar to Wt::Dbo `persist`).
  ```cpp
  class Sample {
    friend class hiberlite::access;
    template<class Archive>
    void hibernate(Archive& ar) {
      ar & HIBERLITE_NVP(name);
      ar & HIBERLITE_NVP(value);
    }
  public:
    std::string name;
    double value;
  };
  // Registration:
  db.registerBeanClass<Sample>();
  ```
- **Extraction Approach**:
  1. Detect `hiberlite.h` includes.
  2. Search for `hibernate(Archive& ar)` template method definitions — the enclosing class is an entity.
  3. Search for `db.registerBeanClass<TypeName>()` — template type argument is the entity.
  4. Table name is derived from the class name by Hiberlite convention (plural or as registered).
- **Key Challenges**: Library is largely unmaintained; codebases using it are rare; table naming convention may require reading Hiberlite source.
- **Analysis Tools**: tree-sitter-cpp, regex: `registerBeanClass<(\w+)>`
- **Complexity**: Medium

## 13. Raw SQL Files Bundled with Project

- **Name**: Raw SQL Schema / Migration Files
- **Type**: Schema File / Migration Tool
- **Supported Databases**: Any (PostgreSQL, MySQL, SQLite, SQL Server, Oracle, etc.)
- **Detection Signals**:
  - File extensions: `*.sql`
  - Common directories: `db/`, `sql/`, `migrations/`, `schema/`, `database/`, `scripts/`, `resources/sql/`
  - File naming patterns: `schema.sql`, `init.sql`, `create_tables.sql`, `V1__*.sql` (Flyway), `*.up.sql`, `*.down.sql`
  - Embedded in resource compilation (Qt `*.qrc` files referencing SQL, MSVC `.rc` files)
- **Entity Definition Style**: Standard SQL DDL.
  ```sql
  CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
    total NUMERIC(10,2)
  );
  ```
- **Extraction Approach**:
  1. Glob for all `*.sql` files in the repository tree.
  2. Parse each file for `CREATE TABLE\s+(\w+|"[^"]+"|`[^`]+`)` patterns.
  3. Also capture `CREATE TABLE IF NOT EXISTS`, `CREATE TEMP TABLE`, `CREATE TEMPORARY TABLE`.
  4. Use a SQL parser (not just regex) to handle quoted identifiers, multiline statements, and comments correctly.
  5. Optionally parse `ALTER TABLE ... ADD COLUMN` for incremental schema evolution.
  6. Check `*.qrc` files for embedded SQL resource references.
- **Key Challenges**:
  - SQL dialect differences (PostgreSQL `$$` quoting, MySQL backtick identifiers) require dialect-aware parsing.
  - Migration files may define tables incrementally across multiple files; reconstructing the final schema requires processing all files in order.
  - `CREATE TABLE` inside stored procedure bodies or conditional blocks may not represent application-facing entities.
- **Analysis Tools**: pg_query (PostgreSQL dialect), sql-parser NPM package, custom regex for simple cases, SQLite `.read` for SQLite DDL
- **Complexity**: Low

## 14. Protobuf Schema Files

- **Name**: Protocol Buffers (Google Protobuf)
- **Type**: Schema File / Serialization Framework
- **Supported Databases**: N/A (serialization format, often used alongside databases)
- **Detection Signals**:
  - File extensions: `*.proto`
  - Dependencies: `protobuf` in `vcpkg.json` (`"protobuf"`), `conanfile.txt` (`protobuf/x.x.x`), `CMakeLists.txt` (`find_package(Protobuf REQUIRED)`)
  - Include patterns: `#include <google/protobuf/message.h>`, generated `*.pb.h` files
  - Build rules: `protobuf_generate_cpp(...)` in `CMakeLists.txt`
- **Entity Definition Style**: `.proto` message definitions.
  ```proto
  message User {
    int64 id = 1;
    string name = 2;
    string email = 3;
  }
  ```
- **Extraction Approach**:
  1. Glob for all `*.proto` files.
  2. Parse `message MessageName { ... }` blocks — each top-level message is a candidate entity.
  3. Identify messages that are likely persisted (look for them being stored in DB calls or embedded in storage-related messages like `StoredUser`, `UserRecord`).
  4. Extract field names and types from each message block.
  5. `service` definitions with `rpc` methods named `Create*`, `Store*`, `Save*` suggest persisted entities.
- **Key Challenges**:
  - Not all Protobuf messages represent database entities; many are just wire format objects.
  - Nested messages may or may not map to separate tables.
  - Protobuf files may be from an external API schema, not internal data models.
- **Analysis Tools**: tree-sitter-proto grammar, regex: `^message\s+(\w+)\s*\{`
- **Complexity**: Medium

## 17. Database Migration SQL Files (Co-located)

- **Name**: Database Migration Files (Flyway, Liquibase SQL, custom)
- **Type**: Migration Tool
- **Supported Databases**: Any
- **Detection Signals**:
  - File patterns: `V[0-9]+__*.sql`, `[0-9]+_*.sql`, `*.up.sql`, `*.down.sql`, `db/migrate/*.sql`
  - Directories: `migrations/`, `db/migrations/`, `flyway/`, `liquibase/`, `database/migrations/`
  - Config files: `flyway.conf`, `flyway.toml`, `liquibase.properties`, `liquibase.xml`, `liquibase.yaml`
- **Entity Definition Style**: Standard SQL DDL in sequentially numbered files.
- **Extraction Approach**:
  1. Identify migration directories by common naming patterns.
  2. Sort migration files by version number/timestamp.
  3. Process files in order, accumulating `CREATE TABLE`, `ALTER TABLE ADD COLUMN`, `DROP TABLE` operations.
  4. Reconstruct the final schema state from the migration sequence.
  5. For Liquibase XML/YAML changelogs, parse `<createTable tableName="...">` elements.
- **Key Challenges**:
  - Migration files may be scattered or use non-standard naming.
  - Rollback scripts (`.down.sql`) should not be included in final schema.
  - Conditional DDL (`IF NOT EXISTS`) requires idempotency-aware processing.
- **Analysis Tools**: SQL parser, XML parser for Liquibase, YAML parser, sorted file glob
- **Complexity**: Medium

## Repository Detection Plan

### Step 1: Identify Package Manager and Build Files
- Scan for `CMakeLists.txt`, `vcpkg.json`, `conanfile.txt`, `conanfile.py`, `*.pro` (qmake)
- Extract library dependencies and `find_package` calls to identify which database frameworks are present

### Step 2: Header Include Scan
- Glob for `*.h`, `*.hpp`, `*.hxx`, `*.cxx`, `*.cpp`, `*.cc` files
- Grep for known include patterns (see Detection Signals for each framework above)
- Build a map of: file → frameworks detected

### Step 3: Framework-Specific Entity Extraction
Run the appropriate extraction strategy for each detected framework:

| Signal Detected | Strategy |
|---|---|
| `#pragma db object` | ODB: parse annotated classes |
| `soci::session` | SOCI: extract SQL strings |
| `QSqlTableModel`, `.setTable(` | Qt SQL: extract `setTable` arguments |
| `dbo::field` / `mapClass<` | Wt::Dbo: parse `persist` methods + `mapClass` calls |
| `REFLECTION(` macro | ORMPP: parse REFLECTION macro arguments |
| `hiberlite::Database` | Hiberlite: parse `hibernate` methods |
| `SQLite::Database` | SQLiteCpp: extract SQL strings |
| `PQexec`, `PQexecParams` | libpq: extract SQL strings |
| `mysql_query` / `sql::Connection` | MySQL connector: extract SQL strings |

### Step 4: Schema and Migration File Scan
- Glob for `*.sql`, `*.proto`, `*.fbs`, `*.capnp` files
- Apply file-type-specific parsers
- For `.sql` files, detect migration patterns and process in version order

### Step 5: SQL String Aggregation
- For all raw-SQL frameworks, collect extracted SQL strings into a unified list
- Apply SQL parser to extract `CREATE TABLE`, `FROM`, `INTO`, `UPDATE`, `JOIN` table references
- Deduplicate and rank by frequency of appearance

### Step 6: Cross-Reference and Confidence Scoring
- Assign confidence scores: `CREATE TABLE` = high confidence; `FROM` clause = medium; `INSERT INTO` = medium; struct annotation = high
- Cross-reference struct/class names found in ORM annotations with SQL table names from raw SQL strings
- Flag tables that appear only in migration files but not in application code (may be legacy/dropped)

### Step 7: Output Entity List
- Produce a list of: entity name, probable table name, source locations, framework detected, confidence score
- Group by database type (relational, document, etc.)
